# 代码审计与业务流程梳理

> 更新时间：2026-05-15
> 审计范围：`hope/` 前台站点、`backend/` API 服务、`backend/admin/` 管理后台
> 审计目标：梳理业务闭环，识别缺失功能、悬空页面、前后端断链，并补充后续可新增功能建议

## 1. 总体判断

当前项目已经从“纯静态展示站”进入“前后端半闭环阶段”。

已经跑通的主链路有：

1. 前台用户注册、登录、找回密码
2. 文章读取、点赞、收藏、评论、阅读历史
3. 心愿提交、社区留言、内测报名
4. 后台对文章、项目、商品、广告、配置、前台用户、心愿单、线索、内测申请的查看与管理

但整体仍然存在 3 类明显问题：

1. 一部分前台页面已经有真实接口，但页面文案、状态管理或数据源仍停留在“前端演示阶段”
2. 一部分页面虽然可访问，但本质还是静态展示页，没有真正业务承接
3. 后台已具备数据能力，但前台不少页面仍未彻底切到后台数据

结论：

1. 项目已具备继续向正式可运营站点推进的基础
2. 当前最需要做的不是继续加页面，而是收口“假数据页面”和“伪闭环页面”
3. 优先级应从“页面补齐”切换到“数据一致性、状态一致性、转化闭环一致性”

## 2. 当前业务结构

### 2.1 前台主业务域

1. 内容域：专栏、文章中心、文章详情、标签聚合、搜索
2. 产品域：产品中心、产品详情、下载与交付中心
3. 游戏域：游戏中心、拼音大冒险、在线轻试玩
4. 实验室域：实验室列表、实验室详情、内测报名
5. 转化域：快来尝鲜、购买页、购买成功页
6. 用户域：注册、登录、找回密码、个人中心
7. 运营域：心愿单、提交心愿、加入社区、下载动态墙、订阅更新

### 2.2 后端当前已承接的数据域

`backend/app/main.py` 已提供这些核心接口：

1. 用户认证与资料：注册、登录、找回密码、个人资料、密码修改、阅读历史
2. 内容：栏目、标签、文章列表、文章详情、文章互动、文章评论
3. 内容聚合：搜索、bootstrap、站点配置、页面配置
4. 项目与商品：项目、商品、广告
5. 用户意向：心愿单、社区线索、内测报名
6. 后台运营：仪表盘、前台用户、心愿单、线索、内测申请、数据库同步、AI 发布

### 2.3 管理后台当前已覆盖的运营能力

1. 内容管理：文章、项目、商品、广告
2. 配置管理：全站配置、页面配置
3. 用户运营：前台用户
4. 线索运营：心愿单、社区线索、内测申请
5. 运营辅助：仪表盘、数据库同步、AI 内容发布

## 3. 已跑通的业务闭环

### 3.1 用户账号闭环

流程：

1. 注册
2. 登录
3. 获取个人资料
4. 修改资料
5. 找回密码
6. 后台查看前台用户与互动统计

判断：

1. 主链路已存在
2. 后台可查看用户
3. 仍缺少更严格的安全校验和真实密码修改体验优化

### 3.2 内容互动闭环

流程：

1. 前台读取文章
2. 登录用户点赞、收藏、评论
3. 阅读行为写入历史
4. 个人中心查看阅读历史
5. 后台按用户查看互动汇总

判断：

1. 是目前最完整的一条真实业务链
2. 文章域已经具备“前台读取 + 用户互动 + 后台统计”的闭环雏形

### 3.3 需求收集闭环

流程：

1. 用户提交心愿
2. 用户在社区页提交联系线索
3. 用户在实验室页提交内测申请
4. 后台统一查看并更新状态
5. 仪表盘统计需求与线索

判断：

1. 数据落库与后台管理已打通
2. 这是当前最接近运营可用的第二条主闭环

## 4. 主要问题清单

### 4.1 高优先级问题

#### 1. 心愿单“列表页”和“提交页”使用了两套完全不同的数据体系

表现：

1. 心愿单列表页仍然直接读本地 `localStorage` store，而不是后端心愿单数据
2. 提交心愿页已经直接调用 `/api/wishlist`
3. 用户在提交页提交的心愿，不会自动体现在心愿单列表页和顶部数量里

证据：

1. [wishlist store](/D:/code/AI/kuntin/hope/src/stores/wishlist.js:7) 仍完全基于 `localStorage`
2. [WishlistPage](/D:/code/AI/kuntin/hope/src/views/WishlistPage.vue:38) 直接遍历 `store.items`
3. [WishlistSubmitPage](/D:/code/AI/kuntin/hope/src/views/WishlistSubmitPage.vue:194) 仍写着“当前为前端演示流程”
4. [API](/D:/code/AI/kuntin/hope/src/api/index.js:203) 只给了 `summary`，`add/remove` 还是假实现

影响：

1. 用户感知会错乱
2. 个人中心与心愿单页的数据来源不一致
3. 后台运营看到的数据与前台用户看到的数据并不一致

建议：

1. 将心愿单统一为后端主数据源
2. 保留本地缓存只做未登录临时态
3. 补齐 `wishlist add/remove/list by user` 真实接口与前台同步逻辑

#### 2. 个人中心的“我的心愿”与前台心愿单页并不一致

表现：

1. 个人中心读取的是后端 `getProfileSummary`
2. 心愿单页读取的是本地 store
3. 用户可能在个人中心看到有心愿，但在心愿单页看到空列表

证据：

1. [UserProfilePage](/D:/code/AI/kuntin/hope/src/views/user/UserProfilePage.vue:67) 通过 `getProfileSummary` 读取远端心愿
2. [UserProfilePage](/D:/code/AI/kuntin/hope/src/views/user/UserProfilePage.vue:379) 明确有“你的心愿单还是空的”分支
3. [WishlistPage](/D:/code/AI/kuntin/hope/src/views/WishlistPage.vue:38) 用本地 store 渲染

影响：

1. 用户中心和业务页状态不一致
2. 收藏、提交、管理三端无法形成统一认知

建议：

1. 心愿单页改成优先使用用户远端数据
2. 未登录用户才退回本地临时心愿单

#### 3. 若干前台页面已经接入真实接口，但文案仍停留在“后续再接后端”的旧状态

表现：

1. 实验室报名页已实际提交 `betaApi.apply`
2. 页面里仍写“后续可直接接入 `beta_applications`”

证据：

1. [LabApply](/D:/code/AI/kuntin/hope/src/views/lab/LabApply.vue:43) 已调用 `betaApi.apply`
2. [LabApply](/D:/code/AI/kuntin/hope/src/views/lab/LabApply.vue:110) 仍写“后续可直接接入 `beta_applications`”

影响：

1. 文档与页面状态误导维护者
2. 审计与验收时容易误判功能完成度

建议：

1. 统一清理这类“旧阶段说明文案”
2. 页面只保留当前真实状态说明

#### 4. 个人中心修改密码的交互字段语义有问题

表现：

1. UI 只有“新密码/确认密码”
2. 调接口时却把“新密码”字段当作 `currentPassword`

证据：

1. [UserProfilePage](/D:/code/AI/kuntin/hope/src/views/user/UserProfilePage.vue:150) `currentPassword: form.password`

影响：

1. 实际接口语义与前端表单不匹配
2. 用户可能无法正确修改密码
3. 后续一旦后端严格校验，会直接报错

建议：

1. 改成“当前密码 / 新密码 / 确认新密码”
2. 与后端接口字段严格对齐

### 4.2 中优先级问题

#### 5. 在线轻试玩页属于典型悬空页面

表现：

1. 页面有“开始游戏”“得分”“时长”“排行榜”
2. 但没有真实游戏逻辑、状态驱动或存档能力

证据：

1. [PlayPage](/D:/code/AI/kuntin/hope/src/views/PlayPage.vue:64) 只有按钮展示
2. [PlayPage](/D:/code/AI/kuntin/hope/src/views/PlayPage.vue:140) 分数是静态展示

判断：

1. 这是“展示型互动稿”，不是实际可玩的业务页面

建议：

1. 要么降级为“试玩预告页”
2. 要么补齐真实小游戏组件、分数状态、开始/失败/重开流程

#### 6. 下载动态墙页属于典型悬空页面

表现：

1. 今日下载、实时活跃、累计下载、实时下载流均为静态假数据
2. 没有后台统计或事件流接口支撑

证据：

1. [DownloadWall](/D:/code/AI/kuntin/hope/src/views/DownloadWall.vue:11) 今日下载为硬编码
2. [DownloadWall](/D:/code/AI/kuntin/hope/src/views/DownloadWall.vue:152) 实时下载流为静态数组

判断：

1. 当前只是品牌展示页，不是数据页面

建议：

1. 短期内改文案，明确为“热度展示页”
2. 中期补 `analytics_events` 或下载埋点数据聚合接口

#### 7. 订阅更新页只有表单外观，没有任何提交能力

表现：

1. 有输入框和按钮
2. 没有提交逻辑、没有接口、没有成功失败状态

证据：

1. [SubscribePage](/D:/code/AI/kuntin/hope/src/views/SubscribePage.vue:14) 只有静态输入和按钮

判断：

1. 属于“已挂路由但未实现业务”的典型辅助页

建议：

1. 如果短期不用，明确标注为预留页并从关键入口弱化
2. 如果要启用，新增订阅数据表、接口与后台管理

#### 8. 下载与交付中心仍偏展示，未形成真实交付中心

表现：

1. 页面会读取商品和产品列表
2. 但没有真实下载地址、交付状态、订单校验、用户已购资源映射

判断：

1. 当前更像“交付说明页”，还不是“交付中心”

建议：

1. 后续增加订单、交付资源、下载凭证、购买记录

### 4.3 低优先级问题

#### 9. 一些旧说明文档仍把项目描述为“待生成代码”或早期静态阶段

表现：

1. `hope/README.md` 仍是很早期的目录介绍
2. 与当前“前后端半闭环”状态不一致

建议：

1. 后续将 README 改成当前真实项目结构和启动方式

#### 10. 审计期发现前后端均存在未提交开发改动

1. 前端 `hope` 和后端 `backend` 当前都不是干净工作树

## 10. 本次审计结论

本项目最核心的优势不是页面数量，而是已经具备了：

1. 可扩展的前台路由体系
2. 已成型的 FastAPI 数据承接层
3. 已可用的 pure-admin 运营后台
4. 文章互动、用户账号、需求收集三条可继续放大的业务主链

当前最大风险不是“没有功能”，而是“页面已经像有功能，但数据并不统一，导致用户和运营对系统状态的理解不一致”。

因此下一阶段最值得做的事是：

1. 去掉假闭环
2. 统一真数据
3. 让用户看到的状态、后台看到的状态、数据库里的状态保持一致
