# 数据说明与后台规划

> 更新时间：2026-04-28
> 适用阶段：前端设计稿完成后，后端一期建设前
> 目标：为后续后台开发、数据库建模、接口定义和管理端规划提供统一基础

## 1. 文档用途

这份文档解决 4 个问题：

1. 这个项目后台到底要管理哪些核心数据
2. 每类数据建议拆成哪些表、字段和状态值
3. 一期上线至少需要哪些 API
4. 后台更适合用什么技术栈实现

本项目不是单一博客，也不是单一商城，而是一个混合型站点：

1. 内容站
2. 产品展示与下载站
3. 游戏与互动站
4. 轻量销售与预付费验证站
5. 实验室与内测承接站
6. 私域与兴趣收集站

所以后台不能只按“文章系统”或“电商系统”来理解，而应按“内容 + 产品 + 转化 + 互动数据”来组织。

## 2. 后台一期目标

建议先做一期最小可用后台，只解决最影响真实运营的 6 件事：

1. 管文章、栏目、标签
2. 管产品、游戏、实验项目
3. 管下载信息、版本信息、交付资源
4. 管心愿单、内测报名、社区线索
5. 管尝鲜商品、订单、支付状态
6. 看基础统计数据与搜索/点击/下载行为

不建议一期就做复杂会员系统、复杂权限系统、复杂消息中心。

## 3. 数据域拆分

建议把整个项目拆成 6 个数据域：

1. 内容域：文章、栏目、标签
2. 展示域：产品、游戏、实验室项目
3. 转化域：尝鲜商品、订单、支付、交付
4. 关系域：心愿单、内测报名、社区线索
5. 互动域：下载事件、轻试玩分数、搜索词、行为埋点
6. 管理域：后台管理员、配置项、页面推荐位

## 6. 一期 API 规划

建议一期规划 15 个核心 API，按 5 组组织即可。这样数量不多，但已经能把静态模拟数据逐步替换成真实数据。

### 6.1 内容接口

1. `GET /api/articles`
作用：文章列表，支持专栏、标签、关键词筛选

2. `GET /api/articles/:slug`
作用：文章详情

3. `GET /api/categories`
作用：获取专栏、专题、分类列表

### 6.2 项目展示接口

4. `GET /api/projects`
作用：产品、游戏、实验项目列表，支持 `project_type` 筛选

5. `GET /api/projects/:slug`
作用：项目详情页数据

6. `GET /api/projects/:id/versions`
作用：下载与交付中心的版本、渠道、更新说明

### 6.3 转化接口

7. `POST /api/beta-applications`
作用：提交尝鲜申请 / 内测报名

8. `POST /api/community-leads`
作用：提交加入社区 / 合作联系

9. `POST /api/wishlist/toggle`
作用：加入或移除心愿单

10. `POST /api/wishlist/state`
作用：修改心愿状态

11. `GET /api/wishlist/summary`
作用：按访客获取心愿单统计和列表

12. `POST /api/orders`
作用：创建订单或创建支付意向

13. `GET /api/orders/:orderNo`
作用：订单详情和支付/交付状态查询

### 6.4 互动与统计接口

14. `POST /api/events`
作用：统一上报下载点击、搜索词、CTA 点击、文章点赞、支付意向等行为

## 9. 推荐后端语言与框架

## 9.1 先说结论

这个项目后台一期更推荐：

**TypeScript + Node.js + NestJS（或 Fastify）+ PostgreSQL**

而不是一开始就用 Python 做主后台。

## 9.2 为什么更推荐 TypeScript / Node.js

1. 当前前端是 Astro，整个项目已经在 JS/TS 生态里
2. 后台一期以内容管理、表单提交、列表查询、订单状态、埋点上报为主，本质是标准 Web CRUD
3. 前后端都用 TypeScript，类型可以复用，接口约束更统一
4. 前端同学和后端同学沟通成本更低
5. 后续如果做 SSR、BFF、同仓 monorepo，会更顺手
6. NestJS 对模块化、DTO、权限、后台管理场景比较友好

## 9.3 Python 适合放在哪

Python 不是不能用，而是更适合做“辅助服务”，不是这期项目的主后台首选。

适合 Python 的场景：

1. AI 内容处理
2. 搜索摘要、关键词提取
3. 数据分析报表
4. 推荐排序实验
5. 后续对接模型工作流

也就是说：

1. 主后台建议 Node.js
2. AI 或分析服务后面可以单独补 Python 微服务

## 9.4 如果团队更熟 Python，能不能直接用 Python

可以。

如果你的团队 Python 明显更熟，建议选：

**Python + FastAPI + PostgreSQL**

但要接受两个现实：

1. 前后端类型共享会弱一些
2. 这类偏内容运营后台项目，FastAPI 的优势没有 AI 项目那么明显

所以最终判断是：

1. 单人独立开发且更偏前端出身：优先 `TypeScript + NestJS`
2. 团队已有成熟 Python 后端能力：可以用 `FastAPI`
3. 后面 AI 能力很重：主后台 `Node.js`，AI 服务 `Python`

## 10. 数据库与部署建议

建议组合：

1. 数据库：`PostgreSQL`
2. 缓存：一期可不强制上 Redis
3. 文件存储：本地开发先本地目录，正式环境用对象存储
4. 后台鉴权：JWT + HttpOnly Cookie 或后台独立 token
5. 部署方式：前后端分离部署，API 单独服务

选择 PostgreSQL 的原因：

1. 内容、订单、报名、埋点都适合关系型建模
2. JSON 字段够灵活，适合先快后稳
3. 后续做筛选、统计、全文扩展更方便

## 11. 一期开发顺序建议

后端别一口气全做完，建议按下面顺序推进：

1. 先建 `projects`、`articles`、`content_categories`、`content_tags`
2. 再建 `beta_applications`、`community_leads`、`wishlist_items`
3. 再建 `project_versions`、`offers`、`orders`
4. 最后补 `analytics_events` 和后台运营看板

对应 API 开发顺序建议：

1. 先做文章和项目读取接口
2. 再做报名、线索、心愿单提交接口
3. 再做订单与下载交付接口
4. 最后做热度、搜索、埋点聚合接口

## 12. 最终建议

如果按“尽快能用、尽快替换前端假数据、后期还能继续扩展”这个目标来判断，推荐方案如下：

1. 后台一期先做 14 张核心表
2. API 一期先做 15 个核心接口
3. 主后台优先选 `TypeScript + NestJS + PostgreSQL`
4. 把 Python 留给后续 AI 与分析服务
5. 先做内容、项目、报名、心愿单，再做订单和运营统计

这样做的好处是：

1. 能最快把当前 `src/data/site.ts` 中的静态内容迁到后台
2. 能把心愿单、内测、社区、下载热度这些假交互变成真数据
3. 能为后续购买链路、下载交付中心和搜索系统打基础
